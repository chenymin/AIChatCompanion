# 第 1 课：让一次输入经过完整调用链

目标：从终端输入追到回复，分清输入处理、模型能力、业务编排与执行记录。预计 2～3 小时，剩余时间用于断点和复述。

检查点：`lesson-01`。本课运行与故障案例均**未执行，待用户验证**；下面是预期，不能作为实测记录。

## 先看问题

我们先实现一个最小的聊天执行过程：接收“突然降温”，调用固定响应的模拟模型，返回正文，并记录各阶段执行情况。本课只有模拟模型，不请求外部服务，不需要 Key，也不保存会话。

```text
终端参数
  → cli.ts：取得输入
  → agent.ts：组织本轮处理
  → providers/mock.ts：返回确定性的模拟回复
  → cli.ts：输出正文

trace.ts：把阶段执行记录输出到 stderr
```

这是后续课程的完整基础版本。当前的“模型”是代码模拟器；成功运行它可以验证调用关系，不能证明真实大模型的回答质量。

## 你今天要读的代码

| 顺序 | 文件 | 只找这些证据 |
|---|---|---|
| 1 | `src/cli.ts` | 如何取得命令行输入；怎样调用业务函数；正文与错误分别写到哪里 |
| 2 | `src/agent.ts` | 一轮处理的先后顺序；模型调用前后记录了什么；错误如何交还调用方 |
| 3 | `src/providers/mock.ts` | 固定响应如何生成；故障开关在哪里生效 |
| 4 | `src/trace.ts`、`src/errors.ts` | runId、阶段和耗时的来源；错误怎样表达 |

先读主函数，再展开调用到的函数。暂时不需要框架、数据库或前端。

## 手动运行与观察

运行环境为 Node `22.22.0`，本课无外部运行依赖、无构建步骤。在仓库根目录执行：

```sh
npm run chat -- '突然降温'
```

预期：终端收到明确标记为模拟的中文回复，同时 stderr 出现执行记录。把不同输入换入命令，观察它们沿同一条业务链路执行。

正文输出到 stdout，trace 输出到 stderr；终端通常会同时显示二者。重定向时可以分开观察：

```sh
npm run chat -- '突然降温' 2> trace.log
```

日志文件只是本次手动实验产物，不应作为“已验证”的依据，直到你确实执行并检查了结果。

## 在 VS Code 中调试

运行：

```sh
npm run debug -- '突然降温'
```

该脚本使用 `--inspect-brk`，会等待调试器连接。使用仓库提供的 VS Code Attach 配置连接后，依次观察：

1. `src/cli.ts` 中取得输入和调用 Agent 的位置。
2. `src/agent.ts` 中调用模拟模型前后的位置。
3. `src/providers/mock.ts` 中返回正文的位置。

每停一次，查看当前输入、函数参数和返回值。区分“进入函数”和“已经取得异步调用结果”，画出实际调用顺序。

## 故障实验：模拟模型失败

先预测会出现哪条 trace、是否仍有正常回复，再执行：

```sh
MOCK_FAULT=error npm run chat -- '突然降温'
```

预期：模拟模型失败，调用方得到错误，终端不输出一份伪装成正常成功的回复；执行记录能帮助定位到失败阶段。本课无数据库，因此没有消息落库或恢复进度。

去掉 `MOCK_FAULT=error` 后，默认模拟路径应恢复。该故障只由显式配置开启，不要求修改或破坏主线代码。
