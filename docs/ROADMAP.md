# Agent 开发课程路线

目标：通过逐步构建、单步调试和原项目对照，形成能迁移到不同业务的 Agent 开发能力。24 课是能力检查点，每课通常安排 3～4 小时；遇到卡点顺延。课程制作与验收时间另外计算。

当前首批制作 01～03 课，其余为计划。所有检查点的运行状态须以各课手动观察记录为准，未执行不能标记为已验证。

## 一个应用，逐课扩展

每个 `lesson-NN` tag 表示该阶段完整参考实现，发布后不移动。学习者从上一课建立练习分支，完成后比较参考解；同一能力保留一个正常案例、一个失败案例和一个未示范变体。

模拟模式提供稳定实验基线，真实模型模式验证供应商接入和任务效果，二者分别记录。前期保持本地 TypeScript 与少量必要接口；按课引入 HTTP、UI、框架和持久化，避免一开始承担完整工程环境。

## 24 个能力检查点

| 检查点 | 本课新增能力 | 观察与调试重点 |
|---|---|---|
| 01 | 最小模拟聊天与阶段 trace | 输入怎样经过编排、生成与输出；故障在哪一层 |
| 02 | ModelClient、配置与真实模型适配 | 配置选择、HTTP 边界、超时与响应解析 |
| 03 | 多轮消息与内存历史 | 准备请求、成功提交、失败不提交、窗口与重置 |
| 04 | 最小 HTTP / 流式界面 | 业务逻辑与传输分离，上游事件与下游正文 |
| 05 | 上下文组装 | 指令、当前输入和业务资料的来源与优先关系 |
| 06 | 结构化分析与校验 | Schema、无效结果、回退与实际模型调用 |
| 07 | 普通 TypeScript Workflow | 固定步骤、条件分支、局部状态和职责 |
| 08 | LangGraph 对照实现 | 用相同案例比较节点、边和 state，识别框架提供什么 |
| 09 | 用户 / Agent 隔离与持久化 | 服务端归属、资源校验、数据初始化与版本 |
| 10 | 历史窗口 | 读取范围、上下文预算与较早信息丢失 |
| 11 | 会话摘要 | 摘要来源、更新时机、事实与压缩损失 |
| 12 | 长期偏好记忆 | 候选、抽取、去重、读取范围和失效 |
| 13 | 工具契约与只读调用 | 参数校验、执行结果与调用证据 |
| 14 | 权限与人工确认 | 允许动作、确认状态、写入前约束与幂等 |
| 15 | 模型选择工具 | 结构化调用意图与实际工具执行的边界 |
| 16 | 有限步行动循环 | 观察工具结果、继续或结束、调用预算与终止 |
| 17 | 跨轮 Workflow Session | 业务进度、版本、缺信息等待与状态提交 |
| 18 | 取消、中断与恢复 | 已产生的副作用、继续起点和重复输入 |
| 19 | 后台任务 | 创建、调度、认领、权限复查与结果保存 |
| 20 | 超时、重试与幂等 | 哪些错误可重试、如何避免重复副作用 |
| 21 | 完善追踪与故障注入 | runId、阶段、调用数、耗时与数据残留 |
| 22 | 任务评测与成本对照 | 确定性规则、生成约束、结果证据与取舍 |
| 23 | 多 Agent 适用性实验 | 单 Agent 与委派方案的收益、代价与执行预算 |
| 24 | 未示范综合扩展 | 学习者独立选择接口、状态、工具和验证方法 |

追踪和失败实验从第 1 课开始，21～22 课进行系统化整理。工具一经引入就约束参数、权限和执行预算；持久化后才讨论跨进程恢复。新依赖须解决当前课的具体问题。

## 与真实项目对照

每课在文档内列出 `ElectronicCompanionAgent` 的相对文件与函数名。原项目提供真实边界，但其陪伴人设、情绪关系分析、Skill 分类和群聊策略并非所有 Agent 的固定结构。

课程核心实现与原项目平台需要区分：Node 本地进程与 Cloudflare Worker / D1 在状态、生命周期、后台执行和事务上存在差异。平台接入在综合阶段按需要映射，不要求前期每课同时维护两套运行环境。

## 独立迁移实践

24 课后安排约 4～6 个学习日，在独立目录实现不同业务，暂定“售后工单助手”：补齐订单问题 → 查询本地模拟订单与政策 → 形成处理方案 → 等待确认 → 创建模拟工单。

先做固定 Workflow，再比较引入有限步模型工具循环的效果。工具数据不足时不虚构结果，写入由程序校验确认与幂等规则。真实退款和外部消息发送不属于该练习。

最终验收要求：

- 从新需求解释规则、单次模型调用、固定 Workflow、模型循环的选择。
- 独立定义自己的业务状态、工具与模型接口。
- 处理缺信息、无权限、失败、取消、重复提交和中断恢复。
- 用手动案例记录任务结果、调用数量和实际耗时，未知项明确列为未验证。
- 处理一个未被演示的新需求，并说明影响范围与验证方法。

## 建议的学习反馈

每课记录五项即可：本课解决的问题、关键差异、实际调用链、正常/失败观察、仍待确认的内容。把问题或推演发回教学对话，反馈后再记录已证明的理解。

课程的核心循环是：**运行上一课 → 发现问题 → 预测改法 → 自己实现 → 手动断点观察 → 对照参考实现与原项目 → 完成新变体。**
